# Этап 12 — учёт токенов и админ-бот

Задача: показать владельцу, кто пользовался помощником, каким режимом и
сколько токенов на это ушло. Отчёты приходят в Telegram отдельным ботом.

## Что появилось

| Что                        | Где                                                            |
| -------------------------- | -------------------------------------------------------------- |
| Счётчик токенов провайдера | `packages/core/src/ai/usage.ts`                                |
| Таблица расхода            | `packages/db/src/schema.ts` → `ai_usage`                       |
| Запросы агрегации          | `packages/db/src/queries/usage.ts`                             |
| Запись расхода на сайте    | `apps/web/src/app/api/chat/route.ts`, `api/assistant/route.ts` |
| Кто спрашивает             | `apps/web/src/lib/usage.ts`                                    |
| Админ-бот                  | `apps/admin-bot`                                               |

## Как считаются токены

Счётчик присылает провайдер, но в двух разных местах и в двух форматах:

- **Потоковый ответ** (`/api/chat`): у OpenAI-совместимых провайдеров счётчик
  приходит в конце потока, если попросить `stream_options.include_usage`.
  У Anthropic входные токены приходят в начале сообщения, выходные — в конце.
- **Обычный ответ** (`/api/assistant`): счётчик лежит в `usage` ответа модели.

`parseProviderUsage` понимает оба формата: `prompt_tokens`/`completion_tokens`
и `input_tokens`/`output_tokens`. В потоке счётчики **не складываются**, а
берутся по максимуму (`mergeUsage`): у OpenAI он приходит один раз целиком, и
сложение дало бы двойной счёт.

Если провайдер счётчик не прислал, расход считается приблизительно по длине
текста (`estimateUsage`), и запись помечается `estimated = true`: в отчёте
видно, что это оценка, а не точные числа.

Сколько токенов ушло на один вызов режима — сумма планировщика поиска и
ответа модели: режимы «Поиск», «Рассуждение» и «Ресёрч» зовут модель дважды.

Ответ из кэша модель не зовёт: запись всё равно появляется, но с нулём
токенов и `cached = true`.

## Повторы при сбое шлюза

Провайдер моделей (APInex) периодически отдаёт 502 — это временный сбой
его шлюза, длящийся секунды. Раньше такой ответ ронял режим целиком:
пользователь видел «не удалось получить ответ», хотя через минуту тот же
вопрос обрабатывался нормально.

Теперь запрос повторяется на временных ошибках (429, 502–524) с паузой
4 и 8 секунд, и только потом уходит к следующей модели цепочки. Ошибки
аккаунта (402 — нет денег или не сделан ежедневный check-in) повтором не
лечатся: там сразу переходим к следующей модели.

## Кто спрашивает

Аккаунтов на сайте нет, и заводить их ради отчёта не нужно:

- **Сайт** — анонимный идентификатор в cookie `shveyka_uid`, ключ `web:<id>`.
  Личных данных в нём нет, он лишь показывает, что один и тот же человек
  приходил снова.
- **Telegram-бот** — бот передаёт заголовками `X-Shveyka-User: tg:<id>` и
  `X-Shveyka-User-Name`. Telegram знает идентификатор каждого человека, и в
  отчёте видно, кто и сколько потратил.

## Админ-бот

Отдельное приложение `apps/admin-bot`: grammY, long polling, токен только из
окружения (`ADMIN_BOT_TOKEN`).

Команды:

| Команда             | Что делает                                           |
| ------------------- | ---------------------------------------------------- |
| `/report`, `/today` | отчёт за сегодня (`/report неделя`, `/report месяц`) |
| `/week`, `/month`   | отчёт за 7 и 30 дней                                 |
| `/user <id>`        | расход одного человека: `tg:12345` или часть ключа   |
| `/top`              | кто потратил больше всех за неделю                   |
| `/modes`            | чем пользовались за неделю                           |
| `/export`           | выгрузка в CSV за неделю                             |
| `/health`           | проверка базы и сайта                                |
| `/ping`             | бот на связи                                         |

Ежедневно в 21:00 по Москве отчёт за день приходит сам (`ADMIN_REPORT_HOUR`).

Бот приватный: отвечает только владельцу. Кто владелец — переменная
`ADMIN_CHAT_ID`, а если она пуста, то первый, кто написал `/start`; чат
запоминается в файле и переживает перезапуск.

Отчёты собираются чистыми функциями в `apps/admin-bot/src/report.ts` — их
можно проверить тестом без базы и без Telegram.

## Переменные окружения

`apps/admin-bot/.env`:

```bash
ADMIN_BOT_TOKEN=            # токен от @BotFather
ADMIN_CHAT_ID=              # пусто — владельцем станет первый /start
ADMIN_REPORT_HOUR=21        # час отчёта по Москве
ADMIN_TOKEN_PRICE_PER_MILLION=0   # цена миллиона токенов: нужно, чтобы считать деньги
SITE_URL=https://shveyka-igolka.ru
```

## Развёртывание

- `Dockerfile.admin-bot` — свой образ: `pnpm --filter @shveyka/admin-bot start`.
- `docker-compose.yml` — сервис `admin-bot` с `env_file: .env, apps/admin-bot/.env`
  и томом `admin-bot-data` под чат владельца.
- `.github/workflows/deploy.yml` — сборка `web bot admin-bot` и запуск
  `docker compose up -d web bot admin-bot caddy`.
- Миграция `0005_large_sandman.sql` создаёт `ai_usage` и применяется в CI
  до старта нового кода.

## Ограничения

- Расход по сайту виден по анонимной cookie: один и тот же человек с разных
  браузеров — разные строки. По Telegram видно точно.
- Счётчик приходит не от всех шлюзов: у части провайдеров он молчит, и
  расход считается приблизительно (помечается в отчёте).
- Ключ `X-Shveyka-User` приходит от бота и не подписывается: подделать его
  может любой, кто умеет отправлять запросы сайту. Для своего отчёта это
  не мешает.
