# Деплой на сервер

Сайт живёт на VPS (`shveyka-igolka.ru`, Caddy с авто-HTTPS). Контейнеры
поднимает `docker compose`: `web` — сайт, `bot` — Telegram-бот, `caddy` —
обратный прокси.

Текущий сервер: `34.88.114.146` (GCP, `europe-north1`).

## Как это работает сейчас

`push` в `main` → GitHub Actions (`.github/workflows/deploy.yml`) подключается
к серверу по SSH и делает:

1. `git pull` в каталоге с репозиторием;
2. `docker compose build web bot` — образы собираются, старые контейнеры
   продолжают работать;
3. `docker compose run --rm web pnpm db:migrate` — схема БД обновляется
   **до** старта нового кода;
4. `docker compose run --rm web pnpm db:check` — проверяется, что база
   доступна и каталог не пуст;
5. `docker compose up -d web bot caddy` — переключение на новые образы
   (caddy тоже: в нём живёт Caddyfile);
6. проверка healthcheck: если контейнер не поздоровался за минуту, деплой
   падает и в лог уходят последние 50 строк.

Шаг 4 — не формальность. Главная страница статическая, поэтому контейнер
может быть «здоров», пока каталог не открывается: база недоступна или пуста.
Без проверки такой деплой выглядит успешным, а сайт не работает.

Ручной деплой не нужен: тот же процесс запускается кнопкой **Run workflow**
в разделе Actions.

## Почему скрипт уходит на сервер файлом

Раньше скрипт деплоя передавался на сервер через stdin: `ssh … bash -s` с
heredoc. Такой способ ломается тихо: первый же `docker compose run`
забирает поток ввода, bash видит конец скрипта и завершается с кодом `0`.
Деплой выглядит успешным, хотя половина шагов не выполнялась — контейнеры
остались на старых образах.

Поэтому скрипт сначала кладётся в файл на сервере, и только потом
выполняется: `cat > /tmp/shveyka-deploy.sh && bash /tmp/shveyka-deploy.sh`.
Содержимое файла контейнер забрать не может.

Второй предохранитель — маркер в конце скрипта: `echo "Деплой завершён."`.
CI ищет его в выводе и считает деплой неудачным, если маркера нет. Так
обрыв на любом шаге приводит к красному прогону, а не к тихому «успеху».

## Настройка (один раз)

### На сервере

Каталог с репозиторием и `.env` должны лежать на сервере. Проверить:

```bash
docker compose ls          # где лежат compose-файлы
ls /opt/shveyka            # или где там репозиторий
cat /opt/shveyka/.env      # DATABASE_URL, NEXT_PUBLIC_SITE_URL, ключи AI
```

В `.env` обязательно:

| Переменная             | Зачем                                                    |
| ---------------------- | -------------------------------------------------------- |
| `DATABASE_URL`         | база Supabase                                            |
| `NEXT_PUBLIC_SITE_URL` | `https://shveyka-igolka.ru` — sitemap, robots, canonical |
| `AI_PROVIDER` + ключ   | провайдер ответа (`relay` + `RELAY_API_KEY`)             |
| `OWNER_KEY`            | необязательно: пусто — личные страницы открыты всем      |

Для режимов с интернетом («Поиск», «Рассуждение», «Ресёрч») нужны ещё:

| Переменная              | Зачем                                                      |
| ----------------------- | ---------------------------------------------------------- |
| `EXA_API_KEY`           | поиск страниц в интернете                                  |
| `APINEX_API_KEY`        | ответы моделей для режимов с интернетом                    |
| `MODELS_FAST`           | необязательно: цепочка моделей для быстрых ответов         |
| `MODELS_REASON`         | необязательно: цепочка моделей для разбора задачи          |
| `MODELS_NAVIGATOR`      | необязательно: цепочка моделей для планировщика поиска     |
| `AI_RATE_LIMIT_PER_MIN` | необязательно: лимит запросов к интернету (по умолчанию 8) |

Двух ключей достаточно: без `MODELS_*` берётся цепочка по умолчанию.
Модели с префиксом `free/` идут по бесплатному тарифу APInex — у него
5 запросов в минуту на аккаунт.

Цепочка — это список моделей через запятую: первая отвечает, остальные
страхуют, если первая не справилась. По умолчанию:

| Назначение         | Цепочка                                                                         |
| ------------------ | ------------------------------------------------------------------------------- |
| `MODELS_FAST`      | `free/gpt-6-luna`, затем `free/qwen-3.8-max`                                    |
| `MODELS_REASON`    | `free/qwen-3.8-max`, затем `free/deepseek-v4-pro-0813`, затем `free/gpt-6-luna` |
| `MODELS_NAVIGATOR` | `free/gpt-6-luna`, затем `free/qwen-3.8-max`                                    |

У «Рассуждения» своя цепочка: модели по-разному держат структуру ответа,
и для разбора задачи нужна та, что пишет развёрнуто и по шагам.

Если ключи не заданы, режимы с интернетом отвечают «Режимы с интернетом пока
не настроены на сервере», а режим «Каталог» работает как раньше. В логах
контейнера это видно по строке `[assistant] режимы с интернетом не настроены`
с именами недостающих переменных:

```bash
docker compose logs web | grep "режимы с интернетом не настроены"
```

Ключи лежат в `.env` на сервере, а не в git: после правки контейнер нужно
пересоздать, иначе он продолжит работать со старым окружением.

```bash
docker compose up -d --force-recreate web
```

Для бота отдельно `apps/bot/.env` с `BOT_TOKEN`.

Без `DATABASE_URL` сайт поднимется (главная статическая), но каталог,
проекты и помощник работать не будут — страницы покажут «Что-то пошло не так».

### Ключ для CI

CI заходит на сервер по ключу. Ключ создаётся один раз:

```bash
ssh-keygen -t ed25519 -C shveyka-deploy -f ~/.ssh/shveyka_deploy
cat ~/.ssh/shveyka_deploy.pub
```

Публичный ключ добавляется на сервер:

```bash
echo "ssh-ed25519 AAAA... shveyka-deploy" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

Приватный ключ (`~/.ssh/shveyka_deploy`, без `.pub`) кладётся в GitHub:
**Settings → Secrets and variables → Actions → New repository secret**,
имя `DEPLOY_SSH_KEY`, значение — всё содержимое файла целиком.

### Переменные GitHub

Там же, во вкладке **Variables**, добавляются:

| Имя           | Значение               | Пример          |
| ------------- | ---------------------- | --------------- |
| `DEPLOY_HOST` | адрес сервера          | `34.88.114.146` |
| `DEPLOY_USER` | пользователь для входа | `root`          |
| `DEPLOY_PATH` | каталог с репозиторием | `/opt/shveyka`  |

Пока `DEPLOY_HOST` или `DEPLOY_SSH_KEY` не заданы, шаг деплоя **пропускается**
без ошибки — репозиторий можно пушить, не поднимая сайт.

### Ключ сервера закреплён в workflow

В `deploy.yml` прописан публичный ключ сервера (`ssh-ed25519`). Если сервер
переедет или ключ сменится — деплой перестанет подключаться, и ключ надо
обновить вручную в файле workflow.

## Домен и переключение сервера

Домен `shveyka-igolka.ru` обслуживается DNS у sprinthost. Пока A-запись
указывает на старый VPS (`77.221.140.72`), сайт открывается на старом
сервере, а новый доступен только по IP и по `34.88.114.146.sslip.io`.

Переключение на новый сервер — четыре шага по порядку:

1. **Открыть 443 в firewall GCP.** В правилах VPC Network для этой подсети
   нужен `tcp:443` (и `tcp:80` для проверки сертификата). Без этого Caddy
   не отдаст HTTPS: сайт будет работать только по HTTP.
2. **A-запись на новый IP.** `shveyka-igolka.ru` и `www.shveyka-igolka.ru` →
   `34.88.114.146`. Старый IP убрать, иначе часть запросов пойдёт туда.
3. **Caddy подхватит домен сам.** Сертификат Let's Encrypt выпускается
   автоматически, когда DNS уже указывает на сервер. Проверить:
   `docker compose logs caddy`.
4. **Обновить `NEXT_PUBLIC_SITE_URL`** в `.env` на сервере — от него
   зависят `sitemap.xml`, `robots.txt` и `canonical` в страницах.

Пока шаг 2 не сделан, Caddy будет повторять попытки выпустить сертификат
и писать об этом в лог — это ожидаемо, а не поломка.

## Если деплой не прошёл

Посмотреть состояние на сервере:

```bash
cd /opt/shveyka
docker compose ps
docker compose logs --tail 100 web
docker compose logs --tail 100 caddy
```

Проверить базу отдельно от сайта:

```bash
docker compose run --rm web pnpm db:check
```

Откатиться на предыдущий коммит:

```bash
cd /opt/shveyka
git log --oneline -5
git checkout <нужный-коммит>
docker compose up -d --build web bot caddy
```

## Отдельно о схеме БД

`pnpm db:migrate` применяет файлы из `packages/db/migrations` по порядку и
помечает применённые в таблице `drizzle.__drizzle_migrations`. Файлы
написаны идемпотентно (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT
EXISTS`), поэтому повторный запуск на уже применённой базе ничего не ломает.

Локальная разработка по-прежнему может пользоваться `pnpm db:push` — он
сравнивает схему с базой и приводит её к состоянию из кода.
